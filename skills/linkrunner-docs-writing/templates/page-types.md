# Page-type outlines

Choose one primary purpose. Adapt these outlines; do not paste every heading into every page. The frontmatter description and first paragraph should not repeat each other.

## Quickstart: get a first working result

1. Outcome and supported starting environment.
2. Only the accounts, permissions, installation, and values needed for this path.
3. Ordered steps with a minimal complete example.
4. A concrete result check and the most likely setup failures.
5. Link to the next task and optional configuration.

Do not turn the first successful result into a tour of every feature.

## How-to: complete an existing user's task

1. State the task and starting assumptions.
2. Explain any decision that changes the steps or payload.
3. Show the selected path, including where changes belong.
4. Verify the intended outcome.
5. Put alternatives and relevant troubleshooting after the main path.

Use separate examples when conditional fields materially change the request.

## Explanation: understand a concept or tradeoff

1. State the question being answered.
2. Explain the model and responsibility boundaries.
3. Give a concrete example and relevant consequences or limits.
4. Link to the task or reference that uses the concept.

Do not manufacture setup steps or a troubleshooting section.

## Reference: look up the exact contract

1. Identify the API, SDK, or configuration and applicable version/platform.
2. Describe inputs, required versus optional fields, defaults, and allowed values.
3. Describe outputs, errors, side effects, and ordering where relevant.
4. Show focused examples and links to how-to guides.

Do not hide field semantics inside a narrative tutorial. Do not claim all platforms are equivalent without checking them.

## Troubleshooting: distinguish a failure's cause

1. State the observable symptom.
2. Give a diagnostic check and explain what each result means.
3. Provide the corresponding corrective action.
4. Explain how to verify recovery and what safe information support needs if it fails.

Do not list speculative causes without a way to distinguish them. Never ask readers to share tokens or private payloads.
